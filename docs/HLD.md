# QuoteOps: High-Level Design

Version 0.1, 7 November 2026. Status: for Yona's review, with the PRD. No code exists. Requirement IDs (F1 to F24) refer to `QUOTEOPS-PRD.md`.

## 1. Binding principles

Each can veto a later choice.

1. Isolation lives in the database. A forgotten filter in application code must not leak a row.
2. A person confirms every value. Price approval is a rule on the server, not a disabled button.
3. No number without a source. Every value and every money line stores where it came from.
4. A request is not an account. Sign-up writes a pending, unverified company that can do nothing until the email is verified.
5. Silence is a bug. A failed upload, PDF or mail shows an error with the cause and the next step.

## 2. System

```
 browser ──https──> Cloudflare ──tunnel──> cloudflared ──> web (FastAPI, port 8091, no host port)
                    (Access in stage 6a)                     │   read-only filesystem, tmpfs /tmp
                                                             ├──> db  (PostgreSQL 16, own volume, own network)
                                                             ├──> files volume (uploads, one folder per company, random names)
                                                             └──> mailer (Graph or provider, Q1) via egress network only
 networks: internal (web, db), edge (tunnel, web), egress (web: mail and Turnstile checks only)
```

A new compose project `quoteops`, its own database and its own tunnel, matching how Saku and FigCraft run on VM110. Nothing listens on the host.

## 3. Components and schema

Application: FastAPI, Jinja templates, psycopg 3. Libraries beyond what Saku uses: one PDF library (ReportLab, BSD licence, pure Python), pinned. Passwords use `hashlib.scrypt` from the standard library.

Each table carries `company_id`. Reasons are in the comments.

```sql
CREATE TABLE company (
  id          TEXT PRIMARY KEY,            -- 'c_' + random hex, never derived from an email
  name        TEXT NOT NULL,
  status      TEXT NOT NULL DEFAULT 'unverified',  -- unverified | active | suspended | deleting
  tax_label   TEXT, tax_rate NUMERIC(5,2),  -- set by the owner; no default, so no rate is assumed
  quote_next  INT NOT NULL DEFAULT 1,       -- number series per company (F14)
  invoice_next INT NOT NULL DEFAULT 1,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  job_next    INT NOT NULL DEFAULT 1001     -- stage 3a: the next job is J-<job_next> (section 13)
);
CREATE TABLE app_user (
  id UUID PRIMARY KEY, company_id TEXT REFERENCES company(id),  -- NULL only for role 'sysadmin'
  email CITEXT NOT NULL UNIQUE,             -- one account per email, across companies, in v1
  pw_hash BYTEA NOT NULL, pw_salt BYTEA NOT NULL,
  role TEXT NOT NULL CHECK ((role = 'sysadmin') = (company_id IS NULL)),  -- sysadmin | owner | estimator | accountant | viewer
  -- stage 2b: CHECK (role IN ('sysadmin','owner','estimator','accountant','viewer')) NOT VALID
  email_verified_at TIMESTAMPTZ, disabled_at TIMESTAMPTZ,  -- a disabled user keeps history (F5)
  consent_version TEXT NOT NULL, consent_at TIMESTAMPTZ NOT NULL  -- F16
);
CREATE TABLE session (
  id_hash BYTEA PRIMARY KEY,                -- hash of the cookie value, so a leaked table cannot sign in
  user_id UUID NOT NULL REFERENCES app_user(id), expires_at TIMESTAMPTZ NOT NULL, created_ip INET
);
CREATE TABLE invite (
  id_hash BYTEA PRIMARY KEY, company_id TEXT NOT NULL, email CITEXT NOT NULL, role TEXT NOT NULL,
  expires_at TIMESTAMPTZ NOT NULL, used_at TIMESTAMPTZ,
  -- stage 2b (section 10): added by ALTER TABLE so the migration runs over older databases
  ref UUID NOT NULL UNIQUE DEFAULT gen_random_uuid(),  -- what the revoke form sends; never the token or its hash
  created_by UUID, created_at TIMESTAMPTZ NOT NULL DEFAULT now()
  -- CHECK (role IN ('estimator','accountant','viewer')) NOT VALID;
  -- UNIQUE (company_id, email) WHERE used_at IS NULL: one pending invitation per address
);
CREATE TABLE job (
  id UUID PRIMARY KEY, company_id TEXT NOT NULL, ref TEXT NOT NULL,   -- 'J-1042', unique per company
  customer TEXT NOT NULL, part TEXT NOT NULL, qty INT NOT NULL CHECK (qty > 0),
  material TEXT, due_date DATE, status TEXT NOT NULL,                 -- draft | review | approved | quoted | won | lost | invoiced
  created_by UUID NOT NULL, created_at TIMESTAMPTZ NOT NULL DEFAULT now()
  -- stage 3a (section 13): UNIQUE (company_id, ref), UNIQUE (company_id, id),
  -- CHECK (status IN ('draft','review','approved','quoted','won','lost','invoiced')) NOT VALID
);
CREATE TABLE drawing (
  id UUID PRIMARY KEY, company_id TEXT NOT NULL, job_id UUID NOT NULL REFERENCES job(id),
  file_name TEXT NOT NULL, mime TEXT NOT NULL, bytes INT NOT NULL, sha256 BYTEA NOT NULL,
  path TEXT NOT NULL,                      -- '<company_id>/<32 random hex>'; never the user's file name
  -- stage 3a (section 13): added by ALTER TABLE so the migration runs over older databases
  created_by UUID, created_at TIMESTAMPTZ NOT NULL DEFAULT now()
  -- FOREIGN KEY (company_id, job_id) REFERENCES job (company_id, id) NOT VALID: never another company's job
  -- CHECK (mime IN ('application/pdf','image/vnd.dxf','image/png','image/jpeg')) NOT VALID; CHECK (bytes > 0) NOT VALID
);
CREATE TABLE job_value (
  id UUID PRIMARY KEY, company_id TEXT NOT NULL, job_id UUID NOT NULL REFERENCES job(id),
  label TEXT NOT NULL, value TEXT, unit TEXT,
  status TEXT NOT NULL DEFAULT 'to_confirm',  -- to_confirm | confirmed | needs_check | not_found
  source TEXT NOT NULL,                       -- principle 3: 'typed by <user> from callout 4'
  confirmed_by UUID, confirmed_at TIMESTAMPTZ
);
CREATE TABLE rate (
  id UUID PRIMARY KEY, company_id TEXT NOT NULL, kind TEXT NOT NULL,  -- machine | setup | tooling_pct | margin_pct
  name TEXT NOT NULL, amount NUMERIC(14,2) NOT NULL, valid_from DATE NOT NULL  -- history kept: a quote uses the rate of its date
);
CREATE TABLE cost_line (
  id UUID PRIMARY KEY, company_id TEXT NOT NULL, job_id UUID NOT NULL,
  label TEXT NOT NULL, hours NUMERIC(8,2), rate_id UUID REFERENCES rate(id),
  amount NUMERIC(14,2) NOT NULL              -- stored, not recomputed later, so an old quote never changes
);
CREATE TABLE document (
  id UUID PRIMARY KEY, company_id TEXT NOT NULL, job_id UUID NOT NULL,
  kind TEXT NOT NULL,                        -- quotation | invoice
  number TEXT NOT NULL, total NUMERIC(14,2) NOT NULL, issued_at TIMESTAMPTZ, pdf_path TEXT,
  UNIQUE (company_id, kind, number)
);
CREATE TABLE audit_event (
  id BIGSERIAL PRIMARY KEY, company_id TEXT NOT NULL, actor UUID, at TIMESTAMPTZ NOT NULL DEFAULT now(),
  what TEXT NOT NULL, subject TEXT            -- ids and field names only, never customer text or drawing content
);
CREATE TABLE support_grant (                 -- operator access to a company: needs the company's approval (PRD section 4)
  id UUID PRIMARY KEY, company_id TEXT NOT NULL, granted_by UUID NOT NULL, ends_at TIMESTAMPTZ NOT NULL
);
```

Isolation: row-level security on every table with `company_id`. Each request opens a transaction and runs `SET LOCAL app.company_id = '<id>'`. The policy is `company_id = current_setting('app.company_id', true)`. The second argument makes an unset setting return NULL instead of raising an error, and a comparison with NULL is never true, so a connection with no company sees zero rows. The web role is not the table owner and has no BYPASSRLS. Administrator pages (F18) connect with a second database role, `qo_admin`. It is granted only `company`, `audit_event`, `support_grant`, a counts view, and column-level SELECT on `app_user` without `pw_hash` and `pw_salt`. It has no access to `session`, and no grant on `job`, `drawing`, `job_value`, `cost_line` or `document`, so the "no content" rule is enforced by the database, not by the page. Since stage 2b part 2 `qo_admin` is the only database login of the separate admin service and may also execute the six `qo_admin_*` functions and the two throttle functions (section 11); it still has no access to `pw_hash`, `pw_salt`, `session`, `invite`, `admin_factor` or `admin_session`.

Sign-in, the session cookie and an invite link are looked up before any company is known, so row-level security would hide the row. `session` has forced row-level security, no policy, and no grant for `qo_web` or `qo_admin`. Five SECURITY DEFINER functions, owned by the NOLOGIN role `qo_definer` (BYPASSRLS, SELECT only on the columns they read, INSERT and DELETE on `session`, and since stage 2a DELETE on `company` and `app_user` for the purge below), with a pinned `search_path` that names `pg_temp` last, every table schema-qualified as `public.<name>`, and EXECUTE for `qo_web` only, do these lookups: `qo_login_lookup(email)`, `qo_session_create`, `qo_session_lookup(hash)`, `qo_session_delete(hash)` and `qo_invite_lookup(hash)`. Stage 2a adds five more with the same properties (section 9): `qo_throttle_check(key, kind, limit, window_seconds, block_seconds)` and `qo_throttle_reset(key, kind)` on the `auth_throttle` table, which has forced row-level security, no policy and no grant for `qo_web` or `qo_admin` (`qo_definer` has SELECT, INSERT, UPDATE and DELETE on it); `qo_company_count()`, which counts the verified companies (status `active`, `suspended` or `deleting`) for the cap; `qo_session_delete_user(user_id)`, which ends every session of a user after a password reset or a verification; and `qo_purge_unverified(seconds, keep)`, which deletes abandoned unverified sign-ups (section 9). TEMPORARY on the database is revoked from PUBLIC, `qo_web` and `qo_admin`, so neither can create a temporary table that shadows one the functions read. Each returns at most one row. An expired session, a disabled user, or a used or expired invite returns none. A session of a user whose company is suspended or deleting, or whose company row is missing, also returns none; a `sysadmin` has no company and is not affected. `qo_login_lookup` also returns `company_status` so sign-in can refuse a suspended or deleting company. `qo_login_lookup` returns the password hash to the web role because scrypt cannot run in PostgreSQL; this is one row per call, behind the sign-in rate limit, and since stage 2b part 2 for company accounts only, never a `sysadmin` row (`role <> 'sysadmin'`), so no administrator's hash reaches the web role and an administrator's address behaves at the public sign-in exactly like an unknown one (section 11). Looking inside a company needs a row in `support_grant`, which the company's Owner creates with an end time. The first `sysadmin` is created by `python -m quoteops create-admin` on the server (section 11); no other code path creates one. The sign-up route cannot set a role, so it can only create owners; an invitation (section 10) can only create an estimator, accountant or viewer. Stage 2b part 1 adds no SECURITY DEFINER function and no privilege. Stage 2b part 2 adds six, callable by `qo_admin` only (section 11). Stage 3a adds none and narrows `qo_web` on `job` to SELECT, INSERT and UPDATE, on `drawing` to SELECT, INSERT and DELETE, and on `audit_event` to INSERT (section 13).

Price approval (F10): one function `approve_price(job)` runs in a transaction and fails unless every `job_value` of the job is `confirmed`. A database trigger repeats the check on the `job.status` change, so a second code path cannot skip it.

## 4. Main flows

Sign-up (F1, F4). Form with email, company name and the terms checkbox; no password. The server checks the Turnstile token when configured (Q2), the rate limit, the global cap of verified companies, and that the email is new. In one transaction it creates the company as `unverified`, the owner as `owner` with an unusable credential, and records consent. It sends a verification link. The owner of the mailbox opens it, chooses the password, confirms the company name and accepts the terms; only then can anyone sign in, and only then does the company count toward the cap, which is checked again at that moment. An account nobody verifies is deleted after 72 hours (section 9).

Sign-in (F2). Rate limit per address and per email. A failure always says the same thing. On success a random session id is set in the cookie, and only its hash is stored.

Value sheet and approval (F8 to F10). The estimator adds values with a source note and confirms each. The Owner sees "7 of 12 confirmed". Approve price is accepted only when all are confirmed. On rejection the screen names the values that block it.

Documents (F14). The PDF is built from stored lines, never from the current rates. The number comes from the company series in the same transaction that inserts the document, so two quotes never share a number.

Delete company (F15). Marks the company `deleting`, blocks sign-in, then removes all rows by `company_id` and the company folder in one job and writes a result line to the log with counts. The privacy policy states that backups hold the data for up to 14 days.

Failure flow. A PDF or upload error returns to the same screen with the cause and the next step, and writes an `audit_event` with ids only. A mail error shows "We could not send the email. Try again, or copy this link." with the link visible to the signed-in user only.

## 5. Decisions and why

- Build, not adopt. ERPNext and Kledo already cover invoices, and the research said so. The owner chose to build. The reason to build is the value sheet and the cost sheet, which they do not give a workshop. Recorded so the next reader sees it was considered.
- Own sign-in, not Cloudflare Access, for strangers. Every person who finishes an Access login uses a seat, including the ones you later reject. Access is used only in stage 6a, for the owner's two emails.
- Row-level security, not only a WHERE clause in the data layer. One forgotten filter is the likely bug. Cost: a transaction setting per request.
- Stored amounts on cost lines and documents. A rate change must not rewrite an old quote.
- Files on a volume, not in the database. Backups of the database stay small. Cost: two things to back up and to delete.
- No antivirus in version 1. A scanner would take a large share of the 5.85 GB. Files are never rendered on the server, and read only once, as they arrive, for the type check of section 13; they are stored and sent back as a download with `nosniff`. Recorded as a known limit.
- ReportLab for PDFs: pure Python, no browser, small.

## 9. Stage 2a: authentication

Delivers F1 to F4, the consent record of F16 and the company cap of F17. Not in 2a: invites, roles other than Owner, user management, company profile, the administrator second factor and pages, the Graph mail backend, jobs, uploads.

Routes. Server-rendered pages, one stylesheet, no script, no request to another site.

| Route | Does |
|---|---|
| `GET /` | Signed in: redirect to `/app`. Anonymous: redirect to `/login` |
| `GET, POST /signup` | Email, company name (1 to 80 characters), terms checkbox. No password field. Consent stored as `draft-0` with the time |
| `GET /verify?token=` | Changes nothing. Account not verified yet: the form below. Already verified: an "Already verified" page with a sign-in link. A token that is not genuine, expired, of another kind or for no account: 400 |
| `POST /verify` | Password, company name (filled in with the stored name, editable), terms checkbox (required), the token, CSRF. Sets the password, `email_verified_at` and the consent; renames the company and sets `status = 'active'` only when it is `unverified`. Answers a page with a sign-in link; does not sign in. When the verified companies already fill the cap and this company is `unverified`: the 403 "Sign-up is closed for now" page, and nothing changes |
| `GET, POST /login`, `POST /logout` | Sign-in, and sign-out that deletes the session row and clears the cookie |
| `GET, POST /forgot`, `GET, POST /reset?token=` | Reset link by mail, then a new password |
| `GET /app` | Placeholder: company name, email, role. An account that is not verified cannot sign in, so it never reaches this page; the template keeps its old "verify your email" banner only because a test that clears `email_verified_at` of a signed-in account still checks it |
| `GET /terms`, `GET /privacy` | Drafts, marked as not yet the published documents |
| `GET /healthz` | Unchanged |

Sign-up. The answer is the same page, byte for byte, whether or not the address has an account. In the request, in this order and the same for every address: CSRF and Origin, the form checks, the network limit (429), the cap of verified companies (the "closed" page; checked before anything about the address, so a full system does not tell either) and the per-address limit (silent). There is no password and no scrypt, so sign-up never answers 503. Then the answer goes out: "Check your email to finish signing up: open the link in it to choose your password. If the email does not arrive within a few minutes, submit the form again." Everything that depends on whether the address has an account runs after it, in a background task (FastAPI `BackgroundTasks`): first the purge of abandoned sign-ups (below); then the lookup; for a new address, a new company (`c_` and 16 random bytes in hex) and its owner in one transaction under the new company's tenant setting, with no cap check and no lock, because an unverified company does not count (the unique email index alone settles two sign-ups of one address); then the mail. The new owner's `pw_hash` is 32 random bytes and `pw_salt` 16 random bytes from `secrets`, new for every account and never shown: no password produces that hash, so nobody can sign in to the account. An account that is not verified yet gets a new verification mail, so signing up again recovers from a lost mail and never touches the stored account; a verified account gets a mail that says it exists and points to the reset page.

Verification and the password. Pre-hijacking is the risk this design removes: if sign-up took a password, an attacker could sign up with a victim's address and a password of the attacker's choice; when the victim later verified the account (from that mail, or after signing up again), the attacker's password would still open it. Here the password is chosen only by whoever opens the link in the mail, that is the owner of the mailbox. Opening the link (`GET /verify`) changes nothing and shows the form while the account is not verified. `POST /verify`, in this order: CSRF and Origin (the pre-session double submit), the scrypt slot, the token (kind `verify`), the account; an account that is already verified gets the "Already verified" page and nothing changes; then the password rules (against the token's address), the company name (1 to 80 printable characters) and the terms, which re-show the form with the errors and change nothing; then the hash; then, in one transaction under the company's tenant setting, the sign-up lock and the cap check (see "Company cap and abandoned sign-ups"; at the cap the closed page, a company deleted meanwhile "Link not valid", and nothing changes), then a compare-and-set: `UPDATE app_user SET pw_hash, pw_salt, email_verified_at = now(), consent_version, consent_at = now() WHERE id = ... AND email_verified_at IS NULL`, which must change one row, else the answer is "Already verified"; `UPDATE company SET name, status = 'active' WHERE id = ... AND status = 'unverified'`, so a suspended or deleting company keeps its status and its name; and `qo_session_delete_user`. Of two submissions of the same link, at once or one after the other, only the first sets a password. The consent recorded at sign-up is replaced by the mailbox owner's. No throttle row is used: the signed token is the gate. The answer does not sign in; it links to `/login`. The company name the attacker typed is shown in the form and can be corrected there.

Company cap and abandoned sign-ups. The cap (`QO_MAX_COMPANIES`, PRD section 6) counts verified companies only: status `active`, `suspended` or `deleting`. Sign-up is cheap (no scrypt), so if an unverified sign-up counted, anyone could fill the cap with made-up addresses without controlling a mailbox. The cap therefore bites where an account becomes real: `POST /verify`, and `POST /reset` (which also verifies). In the tenant transaction, after the hash and before any change, the request takes `pg_advisory_xact_lock` on the sign-up lock id, reads the company's status, and, when it is `unverified` and `qo_company_count()` has reached the cap, answers the 403 "Sign-up is closed for now" page and changes nothing: the account stays unverified and the link keeps working until it expires, so it succeeds if the operator raises the cap. A suspended or deleting company is not activated, so the check does not apply to it. The lock makes the check and the activation one step: of two verifications at the last free place exactly one succeeds. `GET /verify` does not check the cap; it shows the form. The visible check in `POST /signup` stays, with the verified count, so a full system is still announced before anyone signs up. Abandoned sign-ups are deleted by `qo_purge_unverified(seconds, keep)`, which the sign-up background task calls first, under the same advisory lock (so no account is verified while it runs). In one statement it deletes the sessions (defensively; an unverified account cannot sign in), the owners and the companies that are `unverified`, have no user with `email_verified_at`, and are older than `QO_UNVERIFIED_MAX_AGE_HOURS` (default 72) or not among the `QO_UNVERIFIED_KEEP` (default 500) newest unverified companies; at most 500 companies a call, the oldest first. It never touches a company whose status is not `unverified` or a user whose address is verified. A failed purge is logged by class name and the sign-up goes on. There is no scheduler: the purge runs only when somebody signs up and passes the throttles, which is also when unverified companies are created. For this `qo_definer` has, by the owner's approval (2026-11-08), DELETE on `company` and `app_user` (DELETE has no column-level form) and SELECT on `company.created_at`, and nothing more; every SECURITY DEFINER function shares the owner `qo_definer`, so all ten run with those rights, but only `qo_purge_unverified` has a statement that deletes from `company` or `app_user`; the other nine have fixed bodies (four of them delete rows of `session` or `auth_throttle` only), and a test pins the exact privilege set. The conditions of the purge are in SQL, not in the caller. A web process that can call the function can choose its arguments: `qo_purge_unverified(0, 0)` deletes every never-verified company, 500 per call, and never a verified one; this is accepted. The age must exceed the 48 hours of the verification link, so the setting refuses less than 49: a link that still works always finds its account. A company deleted while its owner is filling in the form answers "Link not valid".

Sign-in for an account that is not verified yet fails like a wrong password: its hash is unusable, so the one scrypt fails and the text is the usual one; nothing says "not verified".

Reset of an account that is not verified yet. The reset mail proves control of the mailbox too, so a reset sets the new password, sets `email_verified_at` and activates an `unverified` company in the same compare-and-set transaction, after the same lock and cap check as `POST /verify` (every reset takes the lock; only an `unverified` company is refused at the cap). The consent stays as recorded at sign-up (see the accepted limits).

Work after the answer. `/forgot` does the same: both limits are counted in the request; the lookup, the token and the mail run after the answer. Each background task catches every exception and logs its class name only, never the address or a value. This makes the answer not wait for the work that differs between addresses; it does not make the work take the same time. A residual timing signal can remain: the background work loads the database and the process, and a request that arrives during it may be slower.

Mail failure is silent. Neither sign-up nor `/forgot` tells the user that a mail could not be sent: the answer has already gone, and any visible difference would reveal whether the address has an account. The failure is logged by class name (`OSError` for the file backend, `MailError` for Graph). The sign-up answer therefore tells the user to submit the form again when no mail arrives, which sends a new verification link while the account is not verified (within the per-address limit of 3 an hour).

Passwords. Chosen at the verification link or at reset, never at sign-up. NFKC, 10 to 128 characters, no control character (Unicode category Cc: NUL, tab, newline, escape, DEL and the rest; a password field cannot type them), not the address or its local part, not in a list of common passwords. A password of more than 1024 characters as sent (`passwords.MAX_RAW`) is refused as too long without being normalised: NFKC makes a string at most four times shorter (one character of its result composes from at most four, such as U+1F82 from alpha and three marks; a test scans every code point and checks the worst sequences), so such a password is longer than 128 after normalising as well, and the bound, twice the 512 needed, refuses nothing that was accepted before. Sign-in with such a password runs the one scrypt of the empty string that every too-long password runs, and `hash_password` refuses it too. scrypt with n = 2^15, r = 8, p = 1, 32 bytes, a 16-byte random salt, compared in constant time. Sign-in for an unknown address runs one scrypt against a fixed dummy hash; an account that is not verified yet runs one scrypt against its unusable hash.

scrypt limit. One scrypt needs 32 MiB, and the web container is limited to 512 MiB (the idle app uses about 80 to 100 MB), so anonymous requests must not be able to start many at once. Every scrypt in the process (hashing, checking, the dummy check) runs inside a slot of one `threading.BoundedSemaphore` of `QO_SCRYPT_CONCURRENCY` slots (default 3: about 100 MB). The three routes that hash, `POST /login`, `POST /verify` and `POST /reset`, take the slot first, right after the CSRF and Origin check and before any throttle hit, lookup or database connection, and hold it for the whole request (`passwords.scrypt_slot()`, released in `finally`). The slot is reentrant in one thread: the scrypt inside the request reuses it, so `QO_SCRYPT_CONCURRENCY=1` does not deadlock; a hash or check called outside a slot still takes one on its own. A request waits at most `QO_SCRYPT_WAIT_SECONDS` (default 8) for a slot; then it answers 503 "The service is busy. Try again in a few minutes." with `Retry-After: 5`. Because nothing ran before the slot, a 503 has changed nothing: no throttle hit is counted, no row is written, no mail is sent, and no database connection was opened, so a request that waits holds no connection. A sign-in that the throttle blocks still gets its 429; it holds a slot briefly to find that out. The unknown-address path takes a slot too, so the busy answer does not tell whether an account exists. Sign-up runs no scrypt and takes no slot. The settings are read at the first scrypt; one process has one limit.

Tokens in mail. Nothing is stored. A token is base64url of `email|expiry`, a dot, and base64url of HMAC-SHA256 with `QO_SECRET` over `kind|email|expiry|extra`. The kind is signed but not carried, so a reset token cannot verify. Verification tokens last 48 hours. Reset tokens last 1 hour and carry, as `extra`, a fingerprint of the current password hash, so a token stops working once it is used or the password changes another way. A reset also deletes every session of the user and mails a notice. Every link in mail is built from `QO_BASE_URL`, never from the request.

Sessions. 32 random bytes, URL-safe, in the cookie `qo_session` (HttpOnly, SameSite=Lax, Path=/, Secure unless `QO_COOKIE_SECURE=false`). Only the sha256 is stored, through `qo_session_create`, for 7 days, never extended. A new token on every sign-in. Each request resolves the cookie through `qo_session_lookup`; everything after that goes through the tenant connection of the session's company. A `sysadmin` session opens no page in 2a.

Throttling. In `auth_throttle`, so it holds across restarts and workers. The key is sha256 of `kind|value|QO_SECRET`, never the address. Sign-in counts every attempt that got a scrypt slot, before the password is checked: 5 per address in 15 minutes, then the address is blocked for 15 minutes; 30 per network in 15 minutes, likewise. A correct password clears the address counter. A blocked attempt shows the usual failure text plus "Try again in a few minutes". `/forgot`: 3 per address and 10 per network in an hour; over the limit the answer is the same and no mail is sent. Sign-up: 5 per network in an hour, then 429; and 3 per address in an hour (`QO_SIGNUP_PER_EMAIL`, counted after the network and the cap), over which the answer is the same "Check your email" page, no mail is sent and nothing is created. Accepted: a victim's address stops receiving sign-up mails for an hour after three tries, by design. The network is the socket address, or the header named in `QO_CLIENT_IP_HEADER` when a proxy sets it. The limits are settings.

Sign-in answers. Unknown address, wrong password, disabled user and a missing company give one text. A suspended or deleting company gives "This account is suspended. Contact support", only after a correct password.

CSRF. Every POST must carry an Origin equal to the origin of `QO_BASE_URL` (the Referer's origin only when there is no Origin) and a token in the form. Signed in, the token is an HMAC of the session hash. Before a session exists, it is an HMAC of a random value in a two-hour HttpOnly cookie `qo_csrf`, so a token from another browser does not match. Failure is 403 and changes nothing.

Headers. On every response, errors included: `Content-Security-Policy: default-src 'none'; style-src 'self'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `X-Frame-Options: DENY`. Every page is `Cache-Control: no-store`; the stylesheet is cached for an hour. `same-origin` rather than `no-referrer`: with `no-referrer` a browser sends `Origin: null` on a form POST, which the Origin check must refuse.

Errors and logs. An unhandled error gives a generic 500 page and logs the exception class only. 404, 405 and 422 are generic pages, and so are the 413 and 400 of the request size limit below. No token, password or address is logged, and the image runs uvicorn without its access log, because that log holds the query string.

Request size (since the stage 2b part 2 fix). Every request body, on every route of the web app and of the admin service except the drawing upload of section 13, is at most 16384 bytes (`guard.MAX_BODY_BYTES`); the largest real form is a few hundred bytes. The guard middleware enforces it before any route runs. A Content-Length above the limit is answered 413 before a byte of the body is read. A body without Content-Length (chunked) is read by the middleware, which counts the bytes, stops at the part that passes the limit and answers 413; a body within the limit is then handed to the route whole, so no route ever runs on part of a body and at most the limit plus one part is held. A Content-Length that is not ASCII digits, or two that disagree, is 400 ("Request not understood"). Both answers are the app's generic page with the usual headers, `Cache-Control: no-store` and `Connection: close`. A refused request opens no database connection, takes no scrypt slot, counts no throttle and changes nothing. `GET` and `HEAD` without a body are unaffected. Since stage 3a the one drawing upload route has its own, explicit, larger limit, declared in the table `guard.ROUTE_BODY_LIMITS` by method and exact path (section 13); there is no exemption flag, and the admin service has no such route.

Settings. `QO_SECRET` (at least 32 characters) and `QO_BASE_URL` (https unless cookies are not Secure) are required; the app refuses to start without them. `QO_MAIL` accepts `file` (the default: one 0600 file per mail in `QO_MAIL_DIR`, a tmpfs in compose) or `graph` (section 12, which also lists the four variables it requires). `QO_SCRYPT_CONCURRENCY` (a whole number from 1 to 64, default 3) and `QO_SCRYPT_WAIT_SECONDS` (a number above 0 and at most 3600, default 8; a larger finite value would overflow the semaphore's timeout) set the scrypt limit; raise the first only together with the container's memory limit. `QO_MAX_COMPANIES` (default 20) is the cap of verified companies. `QO_UNVERIFIED_MAX_AGE_HOURS` (a whole number from 49 to 8760, default 72; it must exceed the 48-hour verification link) and `QO_UNVERIFIED_KEEP` (10 to 1000000, default 500) control the purge; the upper bounds keep the values inside a PostgreSQL integer.

Accepted limits.
- The per-network sign-in limit counts every attempt, not only failures: the throttle function counts before the password is known, and only the address counter is cleared on success. Thirty sign-ins from one office in 15 minutes would block it for 15 minutes.
- An attacker can block an address from signing in for 15 minutes by failing five times. The block is per address, so it does not tell whether the account exists.
- A reset or verification link names the address in base64. It is mailed to that address, but a proxy that logs URLs would record it.
- A mail failure on sign-up or `/forgot` is logged, not shown, because showing it would tell whether the account exists. A user whose mail is lost learns it only by its absence.
- There is no separate page to ask for a new verification mail in 2a; signing up again with the same address does it while the account is not verified.
- Anyone can make QuoteOps send verification mails to an address they do not own, by signing up with it. The mail asks nothing of the recipient and its link only lets the mailbox owner choose the password; the per-address limit bounds it to three sign-up mails an hour per address.
- An account that somebody else signed up for exists, unverified, with the company name they typed, until the mailbox owner uses the link (and can correct the name there) or the purge deletes it after 72 hours. It does not count toward the company cap.
- An attacker who creates more than `QO_UNVERIFIED_KEEP` (500) unverified sign-ups within 72 hours evicts the oldest unverified ones, which may include a real user's account that is not verified yet; that user signs up again. A user who verifies within hours of signing up is unaffected, and at the default limits (5 sign-ups per network per hour) this needs many networks.
- Unverified rows can pile up to about `QO_UNVERIFIED_KEEP` plus one before the next sign-up's purge; there is no scheduler, so with no sign-ups old unverified rows stay until the next one.
- The cap can be filled by real, verified accounts: that is the product's normal limit, and the operator raises it or removes companies.
- A user who verifies when the cap is full gets the "Sign-up is closed for now" page at the link, after signing up was still open; its text says no account was created, which is true of a usable account (the unverified one is purged later).
- A reset of an account that is not verified yet verifies it and activates its company, but keeps the consent recorded at sign-up, which may have been given by whoever submitted the address rather than by the mailbox owner. The verification form records the mailbox owner's consent; the reset path does not ask for it in 2a.
- A verification link stays valid for its 48 hours after use; used again it shows "Already verified" and changes nothing. A link opened near the end of its 48 hours can expire before the form is sent; the user then signs up again for a new link.
- The answer to sign-up and `/forgot` does not wait for the lookup, the inserts or the mail, but their timing is not equalised: database and process load from that background work can still leave a timing signal.
- Under a burst of sign-ins, verifications or resets beyond `QO_SCRYPT_CONCURRENCY`, requests wait and after `QO_SCRYPT_WAIT_SECONDS` answer 503. An attacker can make the service busy for everyone this way. The per-network sign-in limit still counts the requests that get a slot; once a network is blocked its requests skip the scrypt and leave the slot at once. Requests answered busy are not counted, so they do not move anyone toward a block. A waiting request holds a worker thread but no database connection; with the default thread pool of 40 a flood can still delay other synchronous requests. The limit is per process: more uvicorn workers multiply it.
- The request size limit bounds what one request holds (16384 bytes plus at most one part of the body as the server delivers it), not how many requests are open at once; that is left to uvicorn and the edge. Before the stage 2b part 2 fix there was no limit, and a password was normalised whole before its length was checked.
- Background tasks run in the web process after the answer. A restart between the answer and the task loses that sign-up's account or mail; submitting the form again recovers it.
- `qo_web` can end every session of any user through `qo_session_delete_user`, as it can already create one through `qo_session_create` (stage 1 record).
- The cap is enforced under an advisory lock in the verification and reset transactions; the cheaper check in `POST /signup` may let a sign-up through that the locked check at the link then refuses. Verifications, resets and purges are serialised by that one lock; each holds it for a few short statements.

## 10. Stage 2b part 1: invites, roles and user management

Delivers F5 and F6 as far as users go: the Owner invites by email with a role, the invitee joins the Owner's company, and the Owner changes roles and disables or enables users. The permission table for job actions (who may confirm a value, approve a price, issue an invoice) is applied in stage 3 together with the jobs; this part only stores and changes the role. Not in this part, and built later: the administrator second factor and pages (F18, F25), the Microsoft Graph mail backend (mail stays the file backend), the company profile, jobs, ownership transfer and deleting users.

Roles. `owner`, `estimator`, `accountant`, `viewer`. A company has exactly one Owner in v1, the user who signed up. Only `estimator`, `accountant` and `viewer` can be invited or given by a role change; anything else, including `owner`, `sysadmin`, an empty value, a value with spaces or in another case, is refused by the server by exact comparison wherever a role is accepted. The database repeats the rule: `invite.role` has a CHECK for the three roles and `app_user.role` a CHECK for the five known values (both `NOT VALID`, so the migration runs over older rows; every new or changed row is checked). The application also refuses an invitation row whose role is not one of the three, should such a row ever exist.

Routes.

| Route | Does |
|---|---|
| `GET /team` | Owner only. The company's users (email, role, active or disabled, verified), the pending invitations (email, role, expiry), "N of M users, counting pending invitations", the invite form (email and a role select with the three roles), and per user a role form and a disable or enable button; none for the Owner's own row. A one-time note from the last action |
| `POST /team/invite` | Email, role, CSRF. See "Invitation" |
| `POST /team/invite/revoke` | `ref`, CSRF. Deletes one unused invitation of the company; the link then fails |
| `POST /team/role` | `user`, `role`, CSRF. New role for one user of the company; writes `audit_event` |
| `POST /team/disable`, `POST /team/enable` | `user`, CSRF. Sets or clears `disabled_at`, ends every session of the user, writes `audit_event` |
| `GET /invite?token=` | Changes nothing. A usable link of an active company: the form below. Anything else: the 400 "Link not valid" page |
| `POST /invite` | Password, terms checkbox, the token, CSRF. See "Joining" |

Access. The `/team` routes need a session whose role is `owner`, whose address is verified and whose company has status `active` (read in the Owner's own tenant transaction, one query per request; an `unverified` company gets the 403 page "This company is not active."; `suspended` and `deleting` already end the session); any other role gets 403 and nothing changes, and a request without a valid session is redirected to `/login` as elsewhere. Every POST checks the Origin and the session CSRF token exactly as `/logout` does (403 otherwise). A target is looked up in the Owner's tenant transaction, so row-level security alone decides what exists: an id of another company finds no row and the answer is 404; the revoke statement has no company filter of its own on purpose. The Owner's own row and the owner row are refused with 403 for a role change, disable and enable, so there is no route to demote the Owner, to create a second owner or to create a `sysadmin`. A role that is not one of the three gets a 400 page. Success answers 303 to `/team` with a one-time note in the cookie `qo_flash` (Path `/team`, HttpOnly, SameSite=Lax, Secure, 60 seconds): a fixed key such as `sent`, signed with an HMAC bound to the session, never user text; `/team` shows it once and deletes the cookie. Nothing secret is put in a URL, and every redirect goes to the fixed path `/team`.

Invitation. `POST /team/invite`, in this order: Origin and CSRF; the address (the sign-up rules) and the role, else the note "Enter a valid email address and choose a role. Nothing was sent."; the cap check (below; over the cap the note says so and nothing changes, not even a throttle counter); the throttles (below); then the answer, the note "Invitation sent.". The answer is the same, byte for byte, whether or not the address has an account anywhere. Everything that depends on that runs after the answer in a background task, as for sign-up: the lookup through `qo_login_lookup`; an address with an account (in this or another company) gets a notice, "someone invited this address to a company on QuoteOps; this address already has a QuoteOps account, so no invitation was created", with a sign-in link and no link to join, and no invitation row is made. One address belongs to one company in v1 (`app_user.email` is unique across the platform), so an existing account cannot join a second company. For a new address the task takes the company lock, checks that the company is `active` and the cap again, deletes the unused invitation of that address in the company and inserts the new one in the same transaction, then, after the transaction has committed, looks the address up again: if it now has an account, the invitation just made is deleted by its hash and the notice is mailed instead of the link; otherwise the link is mailed. The first lookup stays because it avoids a row in the common case. A window remains that no company-side code can close without a cross-company database function: an account created after the second lookup and before the link is read behaves like any account created after the mail was sent, and accepting is stopped by the platform-wide unique email, which rolls the use of the link back. The task catches every exception and logs its class name only; a mail failure is never shown.

The token. 32 random bytes from `secrets.token_urlsafe(32)` (43 characters), mailed in the link `QO_BASE_URL/invite?token=...` (never built from the request). Only its sha256 is stored, as `invite.id_hash`; the raw token is neither stored nor logged. The link works for 7 days (`expires_at = now() + 7 days`) and once. The revoke form sends `invite.ref`, a random UUID, so neither the token nor its hash ever leaves the server.

One pending invitation per company and address. Inviting an address again replaces its unused invitation: the old row is deleted and the new one inserted in one transaction, so the old link fails at once. A partial unique index on `(company_id, email) WHERE used_at IS NULL` holds the rule in the database too. The role of the new invitation is the one just chosen.

User cap. `QO_MAX_USERS_PER_COMPANY` (default 5, PRD section 6) bounds users plus pending invitations: users (active or disabled) + unexpired unused invitations, leaving out a pending invitation of the same address because the new one replaces it, + 1 must be at most the cap. The count runs in the tenant transaction under `pg_advisory_xact_lock(0x514F5445, k)`, where k is the first 4 bytes of sha256 of the company id; the two-key form never collides with the one-key sign-up lock. The request makes this check for the visible note, and the background task makes it again, under the lock, in the transaction that inserts; of two parallel invitations at the last free place exactly one invitation is created. At joining, the invitation already holds its place, so only the users are counted: one more may join while the users are fewer than the cap (this also catches a cap lowered meanwhile); otherwise the 403 "Company full" page, and the invitation stays unused. An expired invitation holds no place.

Throttles. In `auth_throttle`, with keys hashed as for sign-in: `invite_company` with the company id, `QO_INVITES_PER_DAY` (default 20) per company per day, and `invite_email` with the recipient address, `QO_INVITES_PER_ADDRESS_PER_DAY` (default 3) per address per day across all companies (the address counter is counted only when the company counter allows). Window and block are one day. Over either limit the answer is the same "Invitation sent." and nothing is sent or created. The sign-up, sign-in and reset throttles are unchanged.

Joining. `GET /invite` resolves `sha256(token)` through `qo_invite_lookup` (unused and unexpired only), then reads the company's name and status in a transaction under that company's tenant setting; a company that is not `active` (`unverified`, `suspended` or `deleting`) gives the "Link not valid" page. The form shows the company name, the role, the invited address read-only, a password field (`autocomplete="new-password"`) and the terms checkbox with the current terms version; opening it changes nothing. `POST /invite`, in this order: the pre-session double-submit CSRF and Origin (as `/verify`); the scrypt slot, before anything else, so a busy 503 has opened no connection and changed nothing; `qo_invite_lookup`; the password rules against the invited address and the terms, which re-show the form and change nothing; the hash, inside the slot; then one transaction under the invitation's company: the company lock, the company status (`active`, else "Link not valid"), the user count against the cap, and a compare-and-set, `UPDATE invite SET used_at = now() WHERE id_hash = ... AND used_at IS NULL AND expires_at > now() RETURNING company_id, email, role`; no row means "Link not valid". The new `app_user` gets the address, the role and the company from that row, never from the form; any other field sent is ignored. Its `email_verified_at` is now (opening the mailed link proves the mailbox), and the consent version and time are recorded. A unique violation on the address (it got an account elsewhere meanwhile) rolls the transaction back, so the invitation stays unused, and answers "Link not valid". The answer is "Your password is set. Sign in to continue." with a link to `/login`; no session is created. Of two parallel submissions of one link exactly one account is made; an accept racing a revoke ends with a complete account or nothing, because both statements need the unused row. A used, expired, revoked or replaced link gives the same 400 page, byte for byte.

Role change, disable, enable. In the Owner's tenant transaction. A role change writes `audit_event` with `what = 'user.role'` and `subject = 'app_user <id> role <old> -> <new>'`; the session lookup reads the role on every request, so it applies at the user's next request. Disable sets `disabled_at` and calls `qo_session_delete_user`, so every session of the user ends at once; a disabled user cannot sign in (stage 2a). Enable clears `disabled_at` and also calls `qo_session_delete_user`, so a session from a sign-in that raced the disabling never comes back; the user signs in again. They write `user.disable` and `user.enable`. A revoke writes `invite.revoke` with `subject = 'invite <ref>'`. `audit_event` fits as it is: `company_id`, `actor` (the Owner), `at`, `what`, and a `subject` with ids and role names only, never an address. No row is written when nothing changed.

Mail. Both mails go through `mailer(settings)`, the file backend or the Graph backend (section 12). The invitation names the company, with every control character of the stored name replaced by a space and at most 80 characters, so a name cannot add a line or a header; the subject and the recipient are fixed or checked addresses, without CR or LF. On the pages the name is escaped by the templates.

Database. No new SECURITY DEFINER function and no new privilege. The invitee's writes run as `qo_web` under row-level security in a tenant transaction for the company that `qo_invite_lookup` returned; `qo_web` already had SELECT, INSERT, UPDATE and DELETE on `invite` and `app_user` within its own company. `qo_admin` still has no access to `invite`. New columns `invite.ref` (UUID, unique, `gen_random_uuid()`), `invite.created_by` (the Owner; no foreign key, because deleting users is not built) and `invite.created_at`, the two CHECKs and the partial unique index, all added idempotently, so the migration runs twice and over a stage 2a database.

Settings. `QO_MAX_USERS_PER_COMPANY` (1 to 100, default 5), `QO_INVITES_PER_DAY` (1 to 1000, default 20), `QO_INVITES_PER_ADDRESS_PER_DAY` (1 to 100, default 3); whole numbers, refused otherwise with a message that names the variable.

`/app` shows the Owner a link to `/team`; other roles do not see it.

Accepted limits.
- The answer to an invitation is identical for a new address and an address with an account, but `/team` afterwards shows a pending invitation only for the new one, so the Owner learns that the other address has a QuoteOps account. The throttles bound this to 20 addresses per company and 3 tries per address per day. Hiding it would need an invitation row for an address that cannot join, which the design excludes.
- "Invitation sent." also follows a throttled invitation, an address with an account, an invitation that lost the race for the last place under the lock, and one whose background task failed or was lost in a restart. In each case no pending invitation appears on `/team`, which is how the Owner notices.
- A mail failure is logged, not shown. The invitation exists and is listed as pending; inviting the address again replaces it and sends a new link.
- The token is in the query string of the link. It is mailed to the address, but a proxy that logs URLs would record it; it works until used, revoked, replaced or 7 days old. uvicorn runs without its access log.
- One company can use up the per-address limit (3 a day across companies) and so delay invitations of that address by other companies for a day.
- Expired unused invitations stay in the table (no scheduler) until the same address is invited again in that company; they hold no place in the cap.
- Disabled users count toward the cap: they keep their history (F5).
- The company name in the invitation mail is text the Owner chose (1 to 80 printable characters at sign-up); it can contain anything printable, a web address for example.
- The partial unique index makes the migration fail over a database holding two unused invitations of one address in one company. Stage 2a had no route that wrote invitations, so no such database exists.
- `GET /invite` does not check the cap; a full company is reported when the form is sent.

## 11. Stage 2b part 2: administrator identity and second factor

Delivers F25 and decides Q5: the system administrator (`sysadmin`) is created only from the command line on the server, signs in with the same password rules as everyone plus a code from an authenticator app (TOTP), and does so at a separate admin service that shares no database password and no signing key with the public web service. Signed in, the admin service shows who is signed in, when the session ends, and a sign-out button; nothing else. Not in this part, and built later: the administrator pages of F18 (companies, users, suspend, delete, caps, usage), recovery codes (the recovery path is `reset-admin` on the server), the Microsoft Graph mail backend, rate limiting by Cloudflare, a route to disable an administrator, and the tunnel route and hostname of the admin service.

Why a separate service. The owner decided on 8 November 2026 that the admin service may be reachable from the public internet, so its sign-in must be strong on its own. Cloudflare Access may sit in front of it at deployment, but nothing in the code relies on it. A second ASGI application (`quoteops.admin_app`) in its own container keeps the administrator's sign-in, cookie and database rights out of the public process: it connects to PostgreSQL only as `qo_admin` with `QO_ADMIN_PASSWORD`, and the web container never has that password; the admin container never has `QO_WEB_PASSWORD`. It imports none of the web routes (`quoteops.app`, `auth`, `team`), the web connection helpers or the mailer; the headers middleware, the error pages and the CSRF, Origin and address helpers they share live in `quoteops.guard`.

Data. Two tables, both with forced row-level security, no policy and no grant for `qo_web`, `qo_admin` or PUBLIC; only `qo_definer` has the exact privileges its functions need, and the owner (the migration login) owns them.

```sql
CREATE TABLE admin_factor (
  user_id UUID PRIMARY KEY REFERENCES app_user(id) ON DELETE CASCADE,
  totp_secret BYTEA NOT NULL,              -- 20 random bytes, written only by the CLI
  last_counter BIGINT NOT NULL DEFAULT 0,  -- time step of the last accepted code: the replay guard
  created_at TIMESTAMPTZ DEFAULT now()
);
CREATE TABLE admin_session (
  id_hash BYTEA PRIMARY KEY,               -- sha256 of the cookie value; the token is never stored
  user_id UUID NOT NULL REFERENCES app_user(id) ON DELETE CASCADE,
  expires_at TIMESTAMPTZ NOT NULL, created_ip INET
);
```

`qo_definer` gets SELECT on `admin_factor (user_id, totp_secret, last_counter)`, UPDATE on `admin_factor (last_counter)`, SELECT on `admin_session (id_hash, user_id, expires_at)` and INSERT and DELETE on `admin_session`; a test pins the whole privilege set of `qo_definer`. The migration adds both tables idempotently, so it runs twice and over a stage 2b part 1 database; a `sysadmin` in such a database has no factor and cannot sign in until `reset-admin` gives it one.

Functions. Six SECURITY DEFINER functions with the pattern of section 3 (owner `qo_definer`, `search_path = pg_catalog, public, pg_temp`, every table written `public.<name>`), EXECUTE revoked from PUBLIC and `qo_web` and granted to `qo_admin` only:

| Function | Does |
|---|---|
| `qo_admin_login_lookup(email)` | `user_id, pw_hash, pw_salt, totp_secret, last_counter` of a user with role `sysadmin`, no company, not disabled, verified and with an `admin_factor` row; else no row. One row at most |
| `qo_admin_totp_use(user_id, counter)` | `UPDATE admin_factor SET last_counter = counter WHERE user_id = ... AND last_counter < counter`; true when one row changed. One statement, so of two requests with the same code exactly one gets true: the second waits for the first one's row lock and then finds the counter used |
| `qo_admin_session_create(hash, user_id, expires, ip)` | Inserts a session row |
| `qo_admin_session_lookup(hash)` | `user_id, email, expires_at` of an unexpired session whose user is still an active, verified `sysadmin`; else no row |
| `qo_admin_session_delete(hash)`, `qo_admin_session_delete_user(user_id)` | Remove one session, or every session of a user |

`qo_admin` also gets EXECUTE on `qo_throttle_check` and `qo_throttle_reset`, for the admin sign-in throttle, and nothing else new. It keeps no table access to `app_user.pw_hash`, `pw_salt`, `session`, `invite`, `auth_throttle`, `admin_factor` or `admin_session`, and cannot call any of the web role's other functions. `qo_web` cannot call any `qo_admin_*` function. A planted temporary table cannot shadow a table these functions read (tested as for section 3).

Hardening of the public sign-in. `qo_login_lookup` gets `AND u.role <> 'sysadmin'` (same output columns, so `CREATE OR REPLACE` suffices). An administrator's address typed into the public sign-in is an unknown address there: the same page, status and headers, one dummy scrypt, and the same throttle counting. The administrator's hash is no longer reachable by the web role at all. `/forgot` sends nothing for it (as before). Sign-up and invitations treat it as an address without an account; the platform-wide unique email still prevents any account from being created (see the accepted limits).

Command line. On the server, with the owner (migration) database login, never over HTTP:

```
docker compose -p quoteops -f deploy/compose.yaml run --rm migrate python -m quoteops create-admin <email>
docker compose -p quoteops -f deploy/compose.yaml run --rm migrate python -m quoteops reset-admin <email>
```

The `migrate` service has the database host and the owner login, which the commands need; it also has the web and admin role passwords, which `migrate` sets and the commands do not read. `docker compose run` gives the command a terminal, so the password is asked with `getpass`, twice, without echo; with `-T` and a pipe, one line of stdin is the password. It is never taken from the command line (any extra argument or option is refused with the usage text and exit code 2), never printed and never logged, and it must pass the password rules of section 9 against the address. `create-admin` refuses (exit code 1, a message without secrets) an invalid address or an address that has any account; otherwise, in one transaction, it creates the `app_user` row (role `sysadmin`, no company, `email_verified_at` now, `consent_version` `admin` and `consent_at` now, because both are NOT NULL; the scrypt hash of the password) and the `admin_factor` row with 20 random bytes from `secrets`. `reset-admin` works only for an existing `sysadmin`: in one transaction a new password, a new secret, `last_counter` back to 0 and every admin session of the account deleted; a disabled administrator stays disabled. Both print, once, the base32 secret without padding and the URI `otpauth://totp/QuoteOps:<email>?secret=<BASE32>&issuer=QuoteOps&algorithm=SHA1&digits=6&period=30` (the address percent-encoded), with a line saying it is shown only now and cannot be read back. No `audit_event` row is written: `audit_event.company_id` is NOT NULL and an administrator has no company. The commands run as the owner login because the tables have forced row-level security without a policy for it; in compose that login is the database superuser (`POSTGRES_USER`), which row-level security does not bind. No other code creates a `sysadmin`: a test checks that only the CLI module names the role in code and that only `auth.py` (the literal `owner`), `team.py` (the role of the invitation row, which the CHECK limits to three roles) and the CLI insert into `app_user`.

TOTP. `quoteops/totp.py`, standard library only: RFC 6238 on RFC 4226 HOTP with HMAC-SHA1, 6 digits, a 30-second step, and the previous, current and next step accepted (a window of plus or minus one step, about 30 to 60 seconds of slack for a slow typist or a phone clock a little off). The code must be exactly six ASCII digits: spaces, signs, a newline and the digits of other scripts are refused before any comparison counts. Every step of the window is computed and compared with `hmac.compare_digest`, even after a match and even for a malformed code, so the work does not depend on the input. The matched step is returned and recorded by `qo_admin_totp_use`; a step not later than the last recorded one is refused, so a code works once, and after a newer code has been used the older codes of the window stop working.

Sign-in (`POST /login`, one step: email, password, code, CSRF token), in this order, after the request size limit of section 9 (a body over 16384 bytes, whatever field makes it large, is 413 before the slot, any connection or any throttle hit; a password over 1024 characters that fits is refused unnormalised like any too-long password, with the same one scrypt and three HMACs):
1. The pre-session double-submit CSRF check as at the web sign-in (an HMAC with `QO_ADMIN_SECRET` of the random value in the HttpOnly, SameSite=Strict cookie `qo_admin_csrf`) and the Origin (or, without one, the Referer's origin) equal to the origin of `QO_ADMIN_BASE_URL`; else 403, nothing counted.
2. The scrypt slot (section 9, the same limit settings, per process). Busy: 503 with `Retry-After: 5`; nothing was counted or changed and no connection was opened.
3. The throttles, with keys hashed with `QO_ADMIN_SECRET`: kind `admin_login_ip` (`QO_ADMIN_LOGIN_FAILS_PER_IP`, default 20) and `admin_login_email` (`QO_ADMIN_LOGIN_FAILS_PER_EMAIL`, default 5) in `QO_LOGIN_WINDOW_SECONDS` (900), then blocked for `QO_LOGIN_BLOCK_SECONDS` (900). Every attempt that got a slot counts. Blocked: 429 with the generic sentence and "Try again in a few minutes.", and no password or code check.
4. `qo_admin_login_lookup` (only for an address that passes the address rules).
5. Always both checks: one scrypt against the real hash, or against the fixed dummy hash when there is no row; and the code against the real secret, or against a fixed dummy secret. Neither check is skipped because the other failed.
6. Only when both are right: `qo_admin_totp_use`; false (the code was used already, in parallel or before) is the generic failure.
7. Success: the address counter is reset, a session row of the browser's old `qo_admin` cookie is deleted, a new session is created, and the answer is 303 to `/admin`.

Every failure is the same page, byte for byte, with status 400 and the sentence "The email, password or code is not correct.": an unknown address, an invalid address, a company account (owner, estimator, viewer: no factor row, so even the right password and a plausible code fail), a disabled administrator, a wrong password, a wrong, malformed, too early or too late code, a used code. The form is not filled in again, so not even the address is echoed. Each of these paths runs exactly one scrypt and three HMACs (tested by counting). The reason: the admin service may face the internet, and any difference would tell an attacker which part to work on, or that an address is an administrator.

Sessions. 32 random bytes from `secrets.token_urlsafe(32)` in the cookie `qo_admin` (HttpOnly, SameSite=Strict, Path=/, Secure unless `QO_COOKIE_SECURE=false`, no Domain); only the sha256 is stored. The lifetime is `QO_ADMIN_SESSION_HOURS` (1 to 24, default 8), absolute and never extended. Every request resolves the cookie through `qo_admin_session_lookup`, so disabling or demoting the account ends the session at once. The admin service never reads `qo_session`, and the web app never reads `qo_admin`; a cookie of one service sent to the other, under either name, is not a session. `POST /logout` needs the Origin and a token that is an HMAC of the session hash (as the web sign-out), deletes the row and the cookie and answers 303 to `/login`; `GET /logout` is 405.

Routes. `GET`/`HEAD /healthz` (as the web app, through `qo_admin`, with the same constant 503 body), `GET /login`, `POST /login`, `GET /admin`, `POST /logout`, and `GET /` (to `/admin` when signed in, else `/login`); nothing else, no documentation pages, no stylesheet (the pages are unstyled and link nowhere). Unknown paths and wrong methods answer 404 and 405 with `Allow`, as the web app.

Headers. The middleware of the web app (section 9), with its request size limit, on every response, errors included: the same Content-Security-Policy, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `X-Frame-Options: DENY`, and `Cache-Control: no-store`. The web app sends no HSTS header, so neither does the admin service; Cloudflare can add it at the edge. An unhandled error is a generic 500 page, logged by class name only; uvicorn runs without its access log.

Settings. `QO_ADMIN_PASSWORD`, `QO_ADMIN_SECRET` (at least 32 characters) and `QO_ADMIN_BASE_URL` (https unless `QO_COOKIE_SECURE=false`, checked as `QO_BASE_URL`) are required; the admin service refuses to start without them, and does not read `QO_WEB_PASSWORD`, `QO_SECRET` or `QO_BASE_URL`. `QO_ADMIN_SECRET` is separate from `QO_SECRET` so that neither service holds the other's key: the web service cannot mint an admin CSRF token or compute an admin throttle key, and the reverse. `QO_ADMIN_SESSION_HOURS`, `QO_ADMIN_LOGIN_FAILS_PER_EMAIL` (1 to 1000) and `QO_ADMIN_LOGIN_FAILS_PER_IP` (1 to 10000) are whole numbers; `QO_LOGIN_WINDOW_SECONDS`, `QO_LOGIN_BLOCK_SECONDS`, `QO_CLIENT_IP_HEADER`, `QO_COOKIE_SECURE`, `QO_SCRYPT_CONCURRENCY` and `QO_SCRYPT_WAIT_SECONDS` mean what they mean for the web service. The web service still neither requires nor reads any `QO_ADMIN_*` variable.

Deployment. Compose service `admin`: the web image, `uvicorn quoteops.admin_app:app` on port 8092 without the access log, read-only, tmpfs `/tmp`, networks `internal` and `edge`, no ports, 512 MiB, a healthcheck on `/healthz`, started after `migrate`. Its environment is the database host, `QO_ADMIN_PASSWORD`, `QO_ADMIN_SECRET`, `QO_ADMIN_BASE_URL`, the admin and throttle settings, `QO_COOKIE_SECURE`, `QO_CLIENT_IP_HEADER` and the scrypt limits, and not the web or owner passwords, `QO_SECRET` or the mail settings. It is meant for its own hostname behind the tunnel (not configured in this repository); Cloudflare Access in front of it is welcome but not relied on.

Accepted limits.
- The TOTP secret is stored unencrypted in `admin_factor`. Only the `qo_admin_*` functions and the owner login read it, but a database backup or an owner-level compromise holds it; the password hash next to it still has to be broken.
- `qo_admin_login_lookup` returns the password hash and the TOTP secret of an administrator to `qo_admin`, because neither check runs in PostgreSQL: a compromised admin container can read them for an administrator whose address it knows, one row per call. This replaces the stage 1 limit for the web role, which can no longer read any administrator's hash.
- The secret and the URI appear once in the terminal and stay in its scrollback; whoever reads that scrollback has the factor. With `-T` and a pipe, the password passes through whatever feeds the pipe.
- Five failed attempts in 15 minutes lock an address for 15 minutes for everyone, the real administrator included; the lock is per address, so it does not tell whether the address is an administrator. `reset-admin` does not lift it; waiting does, or deleting the `auth_throttle` rows with the owner login.
- The per-network limit (20 attempts in 15 minutes, successes included) is shared by everyone behind one address, and with `QO_CLIENT_IP_HEADER` empty every request behind the tunnel has the tunnel's address.
- A lost authenticator or a forgotten password needs server access (`reset-admin`); there are no recovery codes.
- TOTP does not stop a real-time phishing proxy that relays the password and a fresh code; it stops a stolen or guessed password alone. A code seen over the shoulder works once, for whoever uses it first within its window.
- After one code is used, the other codes of the same window are refused, so two sign-ins within about a minute need two different codes; a phone clock more than about 30 seconds off fails every code.
- The failure paths do the same scrypt and HMAC work, but not the same database work in every case: an address with an admin row joins one more row, and a used code costs one more statement, which only someone who already has the password and a code can reach. "Same time" is approximate.
- `qo_admin` can create an admin session row for any user id through `qo_admin_session_create`, as `qo_web` can a session through `qo_session_create`; the lookup answers only for an active `sysadmin`. `qo_admin` can also call the throttle functions for any key and kind, but cannot compute a web key without `QO_SECRET`.
- `create-admin` and `reset-admin` leave no `audit_event` row (no company), only whatever the server's shell keeps.
- An administrator's address typed into the public sign-up gets a verification mail whose link answers "Link not valid"; invited to a company, it gets an invitation whose link fails at joining (the unique email), and the Owner sees a pending invitation. Before this hardening it got the "account exists" notice. Neither tells anyone that the address is an administrator.
- The commands need the owner login to be the database superuser (as in compose) or another role that row-level security does not bind; a plain database owner is bound by the forced row-level security and is refused.
- The admin pages have no stylesheet, because the admin service serves only the routes listed above.
- The request size limit (section 9) bounds what one admin request holds, not how many are open at once, as for the web app. Its 413 and 400 pages are the admin service's own generic page.

## 12. Stage 2b part 3: the Microsoft Graph mail backend

Delivers PRD Q1. `mailer(settings).send(to, subject, text)` is unchanged for every caller; `QO_MAIL=graph` makes it return a `GraphMailer`, `QO_MAIL=file` (the default) the file backend, which stays for tests and development.

Flow. The owner registered an Entra application "QuoteOps mail" with the application permission `Mail.Send`. An Exchange application access policy fences it to one mailbox, the shared mailbox quoteops@chronyxlabs.com, so a stolen secret cannot send as anyone else. `GraphMailer` asks `https://login.microsoftonline.com/{tenant}/oauth2/v2.0/token` for an app-only token (the client-credentials grant, scope `https://graph.microsoft.com/.default`), then posts `https://graph.microsoft.com/v1.0/users/{sender}/sendMail` with a JSON message (`contentType` Text, one recipient) and `saveToSentItems` false, with the bearer token. Only the web service sends mail, so only the web service gets the settings; `admin` and `migrate` get none, `load_admin_settings` reads no mail setting, and the two services still share no secret.

Settings, required when `QO_MAIL=graph` and not read at all when it is `file`: `QO_GRAPH_TENANT` and `QO_GRAPH_CLIENT_ID` (GUIDs), `QO_GRAPH_CLIENT_SECRET` (1 to 256 characters, no whitespace or control character) and `QO_MAIL_FROM` (the sender, an address that passes the sign-up address rule, at most 254 characters). `QO_MAIL_DIR` is not needed. An error names the variable and never its value; the secret field of the frozen `Settings` is left out of its repr. The values come from `~/.config/quoteops/graph.env` on the server, into `deploy/.env`; `QO_MAIL=graph` is set only on the production server.

The sender is the mailbox's user principal name (its technical sign-in name), not the address people see. Graph addresses the mailbox by its UPN, and the access policy is written for that mailbox; the displayed address, quoteops@chronyxlabs.com, and the displayed name "QuoteOps" come from the shared mailbox itself, not from anything this code sends.

Token. Kept in memory only, never written to disk, to a log or to an error. It is reused until five minutes before it expires. A lock lets one request refresh it at a time; the others wait and then use the new token. A refresh that fails (a non-200 answer, an unreadable answer, no answer) caches nothing, so the next send asks again. The mailer is created once per process, keyed by a hash of its four settings, so the cache serves every request.

Results. 202 is success. A 401 drops the cached token (only if no other request already replaced it) and retries the send once with a fresh token; a second 401 is a failure. 429, 5xx, every other 4xx and every other status are failures with no retry. Redirects are not followed: the opener has no redirect handler, so a 3xx is a failure and the token never goes to another address; the opener also ignores proxy variables. The two base URLs are module constants (`https` only); a test replaces them, and no environment variable can. Each call, token or send, times out after 10 seconds. The timeout applies to each wait on the socket, not to the whole exchange, so a server that sends a byte every few seconds can hold a send longer; it holds only a background task.

Failure and logging. Every failure raises `MailError`, whose message is a fixed phrase and the status number ("token request failed with status 500", "send failed with status 429", "send failed: no answer"); never the reply body, the Graph error text, the secret, the token, the recipient or the subject, all of which can hold personal data. The mailer logs nothing. The call sites already catch every exception and log its class name only (`MailError`), never its text; the password-changed notice after a reset is one of them too (a background task that catches every exception), so a Graph outage cannot turn a completed reset into a 500. A line break in the recipient or subject, or a recipient that is not one plausible address, raises `ValueError` before any network call.

Every mail runs in a background task after the answer (sign-up, `/forgot`, invitations and the password-changed notice). The reset route queues the notice only after the password change has committed and only on the success path, so the 10-second limits delay no answer and a refused or busy reset sends nothing; the notice task catches every exception and logs only the class name. A token reply whose `expires_in` is not a finite number of at most 86400 seconds (24 hours) is an unusable reply: it raises `MailError` and caches nothing. In this compose file the web service reaches the internet through the `edge` network; the separate egress network of section 2 is still a design intent.

202 means queued, not delivered. Graph accepts the message and Exchange sends it later; a bounce, a spam folder or a refused recipient never comes back to the application.

Accepted limits.
- One Graph or Entra outage means no mail until it ends. Nothing is retried, and mails are not queued: a message is lost if its send fails or the process restarts before the background task runs. A user submits the form again, as for the file backend.
- SPF for chronyxlabs.com is in place. DMARC is published with `p=none` (monitoring only, reports to the owner's address) since 2026-11-09. The two DKIM selector CNAMEs are published, but signing for the domain is enabled only after Microsoft finishes provisioning the keys (the status was `CnameMissing` at the time of writing). Tightening DKIM and DMARC remains an owner action before mail goes to strangers: without it such mail is likely to be filtered as spam, and it is required before sign-up opens to the public (stage 6b). The one real test mail went to the owner only.
- The access policy and the secret's expiry are in the tenant, outside the code. An expired secret makes every send fail with status 401 and logs `MailError`; the secret must be renewed and `deploy/.env` changed by hand.
- The token and the secret live in the web process's memory, and the secret in the container's environment, so anyone who can read the container can send as the shared mailbox until the secret is revoked. The access policy limits that to this one mailbox.
- A failed send is visible only as `MailError` in the log, with no status counter or alert.

## 13. Stage 3a: jobs and drawing upload

Delivers F8 (a job with customer, part, quantity, material, due date and one or more drawings in PDF, DXF, PNG or JPG) and the upload parts of F17 (the file, company and monthly job caps of PRD section 6, with a page that says why and what to do). Not in this part, and built later: values, prices, rates, costs and PDFs (3b, 3c and stage 4), reading drawings with a model, a customer list screen, the past-jobs guide, any status but `draft`, a preview of a drawing in the browser (decided in 3b), company deletion and export, administrator pages.

Routes. Server-rendered, no script; every route takes its action from `quoteops/permissions.py`.

| Route | Action | Does |
|---|---|---|
| `GET /jobs` | `view_jobs` | The "Quotes" list of the company's jobs: part and ref, customer, quantity, due date, status, number of drawings; "N of M jobs this month (UTC)" and "X MB of Y MB used by drawings" |
| `GET /jobs/new` | `create_job` | The New job form: Job details (customer with a list of up to 20 earlier customers, part name, quantity, material, due date) and the drawing, with the configured file limit |
| `POST /jobs/upload` | `upload_drawing` (and `create_job` without `?job=`) | Without `?job=`: creates a job with its first drawing. With `?job=J-1001`: adds a drawing to that job. The one streamed route (below) |
| `GET /jobs/{ref}` | `view_jobs` | One job, its drawings with download links, and for owner and estimator the forms to add a drawing, delete one and change the job |
| `POST /jobs/{ref}` | `edit_job` | Changes the five fields; `csrf` form field and Origin as `/team` |
| `GET /jobs/{ref}/drawings/{id}` | `view_jobs` | Downloads one drawing |
| `POST /jobs/{ref}/drawings/{id}/delete` | `delete_drawing` | Deletes one drawing while the job is `draft` |

Permissions. `quoteops/permissions.py` holds one dict, `ACTIONS`, from action to roles: `view_jobs` for owner, estimator, accountant and viewer; `create_job`, `edit_job`, `upload_drawing` and `delete_drawing` for owner and estimator. `require(action)` is a FastAPI dependency on top of `auth.require_user`: no valid session is the usual 303 to `/login` (a suspended or deleting company has no session, section 3); a role outside the set is 403 "Your role can see jobs but not change them..."; then, in the user's tenant transaction, a user whose address is not verified or whose company is not `active` gets 403 as well, so an unverified company can neither create jobs nor upload. Later stages add their actions (confirm a value, approve a price, set rates) to the same dict; none is in it now. A test checks every job route against every role, and that every route under `/jobs` has the dependency.

Data. Added with `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, `CREATE ... INDEX IF NOT EXISTS` and guarded `ADD CONSTRAINT`, so the migration runs twice and over a stage 2b database (tested over the schema of main at 848cb17, `tests/data/schema_848cb17.sql`, with rows in it):
- `company.job_next INT NOT NULL DEFAULT 1001`: the job number series, beside `quote_next` and `invoice_next`. A new job takes `J-<job_next>` by `UPDATE company SET job_next = job_next + 1 ... RETURNING job_next - 1` in the transaction that inserts the job, under the advisory lock below, so refs start at J-1001 in every company and two jobs never share one. A column rather than a table because the company row already exists, is already in the web role's reach and is already locked by that update; a separate counter table would need its own grant and policy. `UNIQUE (company_id, ref)` holds the rule in the database too.
- `UNIQUE (company_id, id)` on `job`, and on `drawing` a composite foreign key `(company_id, job_id) REFERENCES job (company_id, id)` beside the old one on `job_id`, so a drawing row can never point at another company's job, whoever writes it.
- `drawing.created_by` (the uploader) and `drawing.created_at`.
- CHECKs: `job.status` is one of `draft`, `review`, `approved`, `quoted`, `won`, `lost`, `invoiced`; `drawing.mime` is one of `application/pdf`, `image/vnd.dxf`, `image/png`, `image/jpeg`; `drawing.bytes > 0`. The CHECKs and the new foreign key are `NOT VALID`, as in stage 2b: they bind every new or changed row; no route wrote jobs or drawings before this stage.
- Privileges of `qo_web`, cut to the minimum: `job` SELECT, INSERT, UPDATE (no job is deleted in this stage); `drawing` SELECT, INSERT, DELETE (a drawing is never changed); `audit_event` INSERT only (and the sequence), so the web role can append to the trail but can neither read nor rewrite it. Before this stage it had all four on all three. `qo_admin` and `qo_definer` get nothing new; row-level security stays forced and the web role owns no table. No SECURITY DEFINER function is added (a test pins the set of sixteen).

Files. A Docker named volume `qofiles` is mounted only into `web`, at `/var/qo-files` (`QO_FILES_DIR`); `admin` and `migrate` never see it, and every root filesystem stays read-only. The image creates `/var/qo-files` with mode 0700 owned by the container user (uid 10001), and Docker gives a new named volume that ownership. Layout: `/var/qo-files/<company_id>/<32 random hex>` for drawings and `/var/qo-files/<company_id>/.tmp/<32 random hex>.part` for uploads in progress, on the same filesystem so the final rename is atomic; folders 0700, files 0600 (opened with `O_CREAT | O_EXCL | O_NOFOLLOW`). The stored name is random, never derived from the user's file name; `drawing.path` holds `<company_id>/<random>`. The user's file name is kept in `drawing.file_name` for display only, made safe first: the last path component, NFC, no control, format (direction overrides, zero-width characters) or other invisible character, no leading dots or spaces, at most 120 characters with the extension kept.

Caps. `QO_MAX_FILE_MB` (1 to 200, default 25), `QO_MAX_COMPANY_MB` (1 to 100000, default 500) and `QO_MAX_JOBS_PER_MONTH` (1 to 100000, default 50), whole numbers checked like the other settings, with a message that names the variable. One MB is 1048576 bytes. A month is the calendar month in UTC (`created_at >= date_trunc('month', now(), 'UTC')`); a drawing added to an existing job is not a new job. The design mockup says "up to 50 MB"; the PRD says 25 MB and wins, and every page shows the configured limit, not a fixed number. A file of exactly the limit is accepted and one byte more is refused; a company whose drawings would pass its total by one byte is refused (both tested at the boundary).

The upload, in this order. `POST /jobs/upload` is the one route of the table `guard.ROUTE_BODY_LIMITS`, keyed by method and exact path (`("POST", "/jobs/upload")`), whose value is `QO_MAX_FILE_MB` times 1048576 plus `guard.UPLOAD_OVERHEAD` (64 KiB, the multipart framing and the other fields). There is no exemption flag; the admin service passes no table, so everything there keeps 16384 bytes, and so does every other web route, `/jobs/upload/` with a slash included. For this route the guard middleware does not buffer the body: it answers 413 with `Connection: close` before reading when the declared Content-Length is over the route limit (a declared 1 GB is answered at once, without a read), otherwise it hands the route a `receive()` that counts every byte and raises at the message that passes the limit (also for a chunked body without Content-Length), and it adds `Connection: close` to any answer given before the body was read to its end, so a refused body is never read. Then:
1. Before any byte of the body is read: the session, the role, the verified address and the active company (the `require` dependency, which reads no body); the Origin (or, without one, the Referer's origin); with `?job=`, the job, looked up under the company's row-level security (another company's ref is 404, unread); the request type (`multipart/form-data` with a boundary, else 400); the company's cooldown (below; 429, before a slot is taken); and an upload slot.
2. Slots: at most `uploads.MAX_PARALLEL` (4) uploads at once in the process, and at most one per company; a request waits up to 5 seconds for each (polling, so a cancelled wait never keeps a slot) and then answers 503 with `Retry-After: 5` and a sentence that says which. With 25 MB files this bounds what uploads can make the 512 MiB container hold; the body itself is never held (step 3). An upload streams to disk, so the memory of one upload is small: a 25 MB upload held the server at 70 to 71 MB, which is why four slots are allowed. Cooldown: a company whose upload was cut in step 3 (a read that stalled, or the rate rule) may not upload for `uploads.COOLDOWN_SECONDS` (60 seconds). It is kept per company id in a dictionary of the process, in memory, with the end time on the monotonic clock; entries that have ended are removed on every check, so it never holds more than the companies currently paused. It is started only by an upload that stalled or arrived too slowly, after the temporary file is removed, and never for any other refusal (type, size, quota, CSRF, busy, a client that left). It applies to all users of the company and to no other company. The check comes after the session, role, Origin and job checks and before the slot is awaited, so a paused company takes no slot and no body byte is read: the answer is 429 with `Retry-After` in whole seconds, rounded up, and a sentence that says how long the pause lasts, that nothing was stored and what to do; `Connection: close` is added like for any answer given before the body was read. The state is per process: a restart clears it, and with several workers each keeps its own.
3. The body is parsed as it arrives with python-multipart's low-level `MultipartParser` (never `request.form()`, whose spooled file would buffer), at most 10 parts. The non-file fields and all part headers together have the 16384-byte budget of `guard.MAX_BODY_BYTES` (413 past it). Each read of the body waits at most 30 seconds (`uploads.READ_TIMEOUT_SECONDS`); a client that stops sending gets 408 and a client that leaves is dropped. The whole upload also has a minimum sustained rate: from the moment the receive loop starts (`time.monotonic()`), once more than `uploads.RATE_GRACE_SECONDS` (10 seconds) have passed, the bytes received so far (every body byte: headers, fields and file) must be at least `uploads.MIN_BYTES_PER_SECOND` (65536, that is 64 KiB/s) times the seconds beyond the grace, checked after every message; otherwise the read stops, the temporary file is removed, the slots are given back and the answer is the same 408 (and the company's cooldown starts), whose text says the upload stopped arriving or arrived too slowly, that nothing was stored, and to check the connection and try again or upload a smaller file. A client sending exactly at the minimum rate is not stopped. A drip of one byte per second is cut about 10 seconds in. A client that sends steadily at or just above the minimum rate is never stopped by the rule and holds a slot for as long as its file needs (about 400 seconds for 25 MB); that is by design. The rule runs only after a message has arrived, and one read may wait up to 30 seconds, so a client can send X bytes quickly and then one byte just under every 30 seconds: it is stopped at the first message after 10 + X/65536 seconds, up to almost 30 seconds later. This is the burst-and-drip bound on the time one upload holds a slot: X/65536 + 10 + 30 seconds, where X counts every body byte, at most the file limit plus the 64 KiB of multipart allowance (`guard.UPLOAD_OVERHEAD`). For a 25 MB file that is about 441 seconds for a 25 MB file (about 440 seconds without the allowance). A burst followed by complete silence is stopped about 30 seconds after the burst, by the read timeout. A fast upload is never affected, and only this route has the rule.
4. The CSRF token: the form sends the session token (`csrf`) as its first field, before the file. It is compared when its part ends; a file part that starts before a matching token, a second token, or a wrong, empty or another user's token is answered 403 with the usual "Request refused" page and `Connection: close`, before a temporary file is even opened. One mechanism, not two: the token is not also accepted in an `X-CSRF-Token` header. A header would let the check run before the first byte instead of after the first part, but it needs a script, and the pages have none and the CSP forbids one; the form field works with and without a script, and the rule that matters holds: no byte of a file reaches the disk before the session, the role, the company, the Origin and the token are checked. Before the token is checked the route has read only the parts before it and the rest of the message that carries it, in memory and inside the 16384-byte budget.
5. The file part is written to the temporary file as it arrives, counting the bytes (one byte over `QO_MAX_FILE_MB` is 413 at the message that crosses it), computing the sha256 and feeding the type check, so the whole file is never in memory. Measured with tracemalloc in a test: a 25 MB upload streamed in 64 KiB messages peaks at well under a tenth of the file size in Python allocations (about 0.4 MB in the run that set the bound); the peak RSS growth is reported too, but `ru_maxrss` is a lifetime high-water mark and so a weak check.
6. The type, from the content, never from the client's Content-Type: PNG by its 8-byte signature followed by an `IHDR` chunk; JPEG by `FF D8 FF`; PDF by `%PDF-` within the first 1024 bytes (a `%%EOF` is not required); DXF as text over the whole file, checked as it streams: it decodes as UTF-8 or as cp1252, has no NUL byte, begins (after an optional BOM and whitespace) with the group code `0` on its own line and then `SECTION`, and contains `ENDSEC` or `EOF`. Whatever the signature, a file whose first 1024 bytes contain `<script` or `<html` (any case) is refused. Everything else is refused: SVG, HTML, ZIP and Office files, executables, a binary DXF, an empty file. The extension of the safe name must agree with the type found (`.pdf`, `.dxf`, `.png`, `.jpg` or `.jpeg`, any case): `a.pdf` holding PNG bytes is refused, and a name of only dots has no extension and is refused.
7. The fields: customer (required, at most 120 characters), part name (required, 120), quantity (ASCII digits, 1 to 1,000,000), material (optional, 100), due date (optional, `YYYY-MM-DD`, today or later in UTC: "This date has passed. Pick today or a later date."; editing may keep a job's old date). Text is trimmed and NFC-normalised, and a character that `str.isprintable()` refuses (control and format characters, line breaks) is refused; text is stored as text and escaped on every page by the templates.
8. In one tenant transaction under `pg_advisory_xact_lock(0x514F4A42, k)` (k as for the team lock of section 10, from the company id; the first key differs, so invitations do not wait for uploads): the company is still `active`, the monthly job count (when creating), the company's bytes plus this file, the job row with its ref (when creating), the drawing row, the audit rows, and then the rename of the temporary file to its random final name. The lock makes "check, insert, rename" one step: of two uploads at the last free megabyte, exactly the free amount is admitted, and of two creations at the last allowed job exactly one succeeds (tested with the in-process company slot switched off, so the database lock is what is tested). If the commit fails, the final file is removed.
9. Success is 303 to `/jobs/{ref}`. A refusal (wrong type, wrong extension, empty, too large, a quota, a field) answers the form again with the cause and the next step in plain words and the fields as typed; a file input cannot be filled in again, so the page asks to choose the drawing again. A refusal by role, session, company or Origin is answered before the body is read, so there are no fields to keep; the page says what is wrong. The temporary file is removed on every exit path (`finally`), and the process and company slots are given back.

At start-up the web app removes temporary files older than one hour from every company's `.tmp` folder (a crash or restart mid-upload leaves them); it never follows a symlink.

Download. `GET /jobs/{ref}/drawings/{id}` streams the file to a signed-in member of the same company (any of the four roles), as `Content-Type: application/octet-stream` with `Content-Disposition: attachment; filename="<ASCII fallback>"; filename*=UTF-8''<percent-encoded safe name>` (no quote, CR, LF, slash or backslash can reach it), `X-Content-Type-Options: nosniff`, `Cache-Control: no-store` and `Content-Security-Policy: sandbox; default-src 'none'`, never inline. The guard sends its own CSP as well; a browser enforces both. The row is read in the tenant transaction, so an id of another company, an unknown id, a malformed id or a ref that does not match gives the same 404 page. The stored path is then resolved with `realpath` and must lie directly inside `/var/qo-files/<the session's company>/` with a random stored name; anything else (another company's folder, `..`, an absolute path, a symlink out) is the same 404 and one log line with the drawing and company ids. The file is opened with `O_NOFOLLOW`.

Delete. Owner and estimator, while the job is `draft` (every job is in 3a), with the session CSRF token and the Origin: the row is deleted and audited in the transaction, then the file is removed. A removal that fails is logged by class name and ids and leaves an orphan file that no row references. A job may be left with no drawing.

Audit. `job.create` (`job <id> fields customer,part,qty,material,due_date`), `job.update` (`job <id> fields <the names that changed>`, no row when nothing changed), `drawing.upload` and `drawing.delete` (`drawing <id> job <id>`), with the actor and the company. Never customer text, a file name or content.

Logs. Class names and ids only: never a file name, customer text or content (tested by uploading names and a customer marked with one word and searching every log record for it).

Pages. The left navigation shows only what works: Quotes (`/jobs`) for everyone, New job for owner and estimator, Users (`/team`) for the owner; Overview, Rates, Company and Roles are not shipped. The New job page has the Job details panel and the drawing area of the mockup, but in the order the form is sent: the token, the five fields, then the file, so that a refusal at the file still finds every typed field; on a wide screen the two sit side by side. The Create job button relies on the browser's `required` fields (customer, part, quantity, drawing) instead of a disabled state, which needs a script. `/app` links to the list.

Accepted limits.
- The process slots, the company slot and the cooldown live in one process; more uvicorn workers multiply them. The advisory lock and the quotas hold across processes.
- Slow uploads. The protections are the rate rule (10 seconds of grace, then 64 KiB/s), the cooldown (60 seconds per company, per process, in memory, for all users of the company, started only by an upload that stalled or arrived too slowly), four process slots and one slot per company. The cooldown works against below-rate accounts: a below-rate account is cut after about 12 seconds and then pays the 60-second cooldown, so it holds a slot for about 12 seconds per account per 72 seconds. The cooldown also pauses a company's honest users for 60 seconds after one slow upload. The state is per process, in memory; several workers each keep their own. The residual limit is a sustained attack, and the cooldown does not stop a client that sends at or above the minimum rate. Such a client is never cut by the rate rule, and a burst followed by a drip of one byte just under every 30 seconds is cut only at the burst-and-drip bound (about 441 seconds for a 25 MB file, X/65536 + 10 + 30 seconds in general). Its upload ends without a cooldown (a cooldown starts only after a stall or a too-slow cut), and it can end with invalid content, so that no quota is used. It follows that several verified company accounts can each hold one slot for roughly 410 to 441 seconds and repeat: four attacker companies can occupy all four process slots almost continuously, and every other company then sees 503 (busy) apart from the gaps between the attackers' uploads. Nothing is stored, no data is exposed and the rest of the application is unaffected. What bounds it: the cap of 20 verified companies, the need for a real verified account for each slot and for about 64 KiB/s of real bandwidth per held slot, and the operator, who can suspend a company. What the app does not have is the following. There is no per-IP throttle (the Cloudflare client-IP header is not configured yet), no per-company limit on upload attempts per hour, no cooldown after an upload that ended in a refusal, and no total deadline shorter than the file needs at the minimum rate. The app also writes no log line for a cut upload or a 503 answer (access logging is off), so the operator has no direct record of which company holds the slots. These tightening options exist and are the owner's decision: a shorter total deadline, a higher minimum rate, a limit on upload attempts per company or per IP once the client-IP header is configured, a log line for cut uploads; none is built.
- The CSRF token is checked when its part ends, not before the first byte: a same-origin request with a session but a wrong token makes the server read the parts before it (inside the 16384-byte budget) and the message that carries it before the 403.
- The type check reads signatures, not structure: a PNG, JPEG or PDF that is truncated or corrupt after its signature is accepted, and so is anything after the first 1024 bytes of such a file. The files are never opened or rendered by the server and are only ever sent back as attachments with nosniff and a sandbox policy. There is no antivirus (section 5). A binary DXF is refused.
- A DXF in a text encoding other than UTF-8 or cp1252 (UTF-16, for example) is refused.
- A failed removal after a delete leaves an orphan file; nothing lists or removes orphans in this stage. A crash between the rename and the commit can leave one too.
- A file input cannot be refilled, so after any refusal the drawing is chosen again.
- "Today" is the UTC date. For a company in Indonesia the UTC date is still the previous day until 07:00 WIB, so in those hours the local yesterday is accepted as a due date.
- Disk use of the temporary files is bounded by the slots and the file cap, not by the company cap, which is checked when the upload has arrived.
